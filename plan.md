# Payment Processing Simulation — Implementation Plan

## 1. Objective

Implement a small Node.js payment-processing microservice that simulates asynchronous payment processing.

The service must:

- use NestJS with the default Express adapter
- be written in TypeScript with strict mode enabled
- expose REST endpoints for creating, retrieving, and updating payments
- simulate asynchronous payment processing
- use JSON file persistence
- protect JSON writes from concurrent corruption
- validate incoming requests
- implement clear error handling
- use NestJS logging
- include unit and API tests
- expose Swagger/OpenAPI documentation
- remain simple and suitable for a technical assignment

Do not introduce unnecessary infrastructure such as MongoDB, PostgreSQL, Redis, RabbitMQ, Kafka, Docker Compose, authentication, CQRS, or event sourcing.

# 13. Serialized File Access

The JSON file implementation must avoid lost updates.

Do not implement concurrent modifications as:

```text
read
modify
write
```

without synchronization.

All mutation operations must execute inside the same serialized queue/mutex boundary:

```text
enqueue mutation
    ↓
read latest file
    ↓
apply change
    ↓
write latest state
    ↓
complete queue item
```

A previous failed write must not permanently block the queue.

A simple serialized Promise queue is acceptable.

Concept:

```ts
private writeQueue: Promise<void> = Promise.resolve();
```

Ensure rejection recovery before chaining the next operation.

Example pattern:

```ts
this.writeQueue = this.writeQueue.catch(() => undefined).then(operation);
```

A small internal mutex helper is also acceptable.

Do not add Redis or an external locking service.

---

# 14. Atomic File Replacement

Where practical, make JSON writes safer by writing to a temporary file first and replacing the main file.

Example flow:

```text
payments.json.tmp
       ↓
successful write
       ↓
rename
       ↓
payments.json
```

This protects against partially written JSON files if a write operation fails midway.

Keep this implementation simple.

Implement:

```ts

```

Flow:

1. Generate payment ID.
2. Set:

```text

```

3. Set `createdAt`.

5. Persist through repository.
6. Log payment creation.
7. Start async payment processing.
8. Return the newly created payment immediately.

The HTTP request must not wait until processing completes.

# 17. Async Processing Trigger

Do not do:

```ts
await this.paymentProcessor.process(payment.id);
```

because it would make POST wait for the simulated processing.

Start the processing in a fire-and-handle manner.

Concept:

```ts
void this.paymentProcessor.process(payment.id).catch((error: unknown) => {
  // log error
});
```

Avoid unhandled Promise rejections.

The POST endpoint should normally return while the payment is still `pending` or has just started processing.

# 22. Processor-Owned State Changes

The processor may perform:

```text
PENDING → PROCESSING
```

# 23. Cancellation Race Condition

Handle this scenario:

```text
POST payment
payment = PENDING

client PATCHes payment to CANCELLED

background processor starts
```

Before the processor moves the payment to `PROCESSING`, retrieve the latest payment state.

If it is already:

```text
CANCELLED
```

stop processing.

Similarly, after the processing delay, retrieve the latest version before updating again.

Do not overwrite a terminal state blindly.

This prevents a cancelled payment from later becoming succeeded.

---

# 24. Allowed State Transitions

Implement explicit state transition rules.

Internal processor transitions:

```text
PENDING → PROCESSING
PROCESSING → SUCCEEDED
PROCESSING → FAILED
```

Public/client transition:

```text
PENDING → CANCELLED
```

Terminal states:

```text
SUCCEEDED
FAILED
CANCELLED
```

No transition is allowed from terminal states in this draft.

Any invalid transition should return or throw a domain-specific conflict error.

| Operation                      | Result       | HTTP |
| ------------------------------ | ------------ | ---: |
| Create valid payment           | Created      |  201 |
| Invalid create input           | Bad request  |  400 |
| Retrieve existing              | Success      |  200 |
| Retrieve missing               | Not found    |  404 |
| Cancel pending payment         | Success      |  200 |
| Invalid status value           | Bad request  |  400 |
| Invalid state transition       | Conflict     |  409 |
| Unexpected persistence failure | Server error |  500 |
| Health check                   | Healthy      |  200 |

# 51. Acceptance Criteria

Implementation is complete when all of the following are true.

## Build

```bash
npm run build
```

passes without TypeScript errors.

## Unit tests

```bash
npm test
```

passes.

## E2E tests

```bash
npm run test:e2e
```

passes.

## Create Payment

Calling:

```http
POST /api/v1/payments
```

with:

```json
{
  "amount": 100,
  "currency": "CAD"
}
```

returns `201`.

## Persistence

Restarting the application does not lose already stored payments.

## Async processing

A newly created payment automatically transitions through:

```text
pending
processing
succeeded/failed
```

without keeping the POST request open for the entire processing duration.

## Cancellation

A pending payment can be cancelled.

A cancelled payment can never later become succeeded or failed.

## Validation

Invalid input returns `400`.

## Missing payment

Unknown ID returns `404`.

## Invalid lifecycle transition

Invalid transition returns `409`.

## Concurrency

Concurrent JSON writes do not lose valid payment records or corrupt `payments.json`.

## Swagger

Swagger UI is available at:

```text
/api/docs
```

## Logging

Meaningful lifecycle events are logged through NestJS `Logger`.

# 55. Important Design Intent

Keep the solution intentionally small but architecturally clean.

The implementation should demonstrate:

- NestJS module structure
- dependency injection
- strict TypeScript
- REST API design
- DTO validation
- business state transitions
- asynchronous programming
- persistence abstraction
- concurrency awareness
- error handling
- logging
- unit testing
- E2E testing
- API documentation

The goal is not to reproduce a real banking platform.

The goal is to provide a clean, testable, understandable microservice that directly satisfies the assignment requirements while showing strong backend engineering practices.

One thing I deliberately added for Codex is the **cancellation race-condition requirement**. Without it, a user could cancel a `pending` payment while the background processor later overwrites it to `succeeded`, which would be an important correctness bug in this architecture.
